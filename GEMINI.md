# UniCORE — Правила и автоматизация проекта

## Профиль проекта
- **Движок**: Godot 4.0.stable (official 92bee43ad)
- **Исполняемый файл**: `C:\Godot\godot.exe` (консольный вывод: `C:\Godot\Godot_v4.0-stable_win64_console.exe`)
- **Директория для тестов**: строго `res://tests/` (запрещено создавать тестовые скрипты `test_*.gd` в корне проекта!)
- **Архитектура**: Модульное ядро, Detroit Liquid Glass UI, P2P & Agent
- **Документация**: `ARCHITECTURE.md`, `ROADMAP.md`

### Специфика синтаксиса и совместимости Godot 4.0-stable:
1. Запрещен вызов `ClassName.has_method(...)` напрямую на имени класса (в 4.0 это фатальная ошибка компиляции `Cannot call non-static function 'has_method()' on the class directly`). Вызывать статические методы напрямую или проверять экземпляры.
2. Захват примитивов (`bool`, `int`, `float`) во внешних замыканиях лямбд передается по значению (`by-value`). Для фиксации изменений внутри лямбды заворачивать примитивы в контейнер: `var done = [false]; var cb = func(): done[0] = true`.
3. `Callable.bind(...)` добавляет связанные аргументы *в конец* сигнатуры после аргументов, переданных вызовом.
4. Проверка синтаксиса: `& "C:\Godot\godot.exe" --headless --path c:\dev\UniCORE --check-only`.
5. Единый запуск всех тестов: `& "C:\Godot\Godot_v4.0-stable_win64_console.exe" --headless --path c:\dev\UniCORE -s res://tests/test_runner.gd`.

## 1. Принцип «Reuse First» (Готовые модули и интернет-поиск)

1. **Запрет на изобретение велосипеда**:
   - Перед разработкой любой нетривиальной подсистемы (P2P-сеть, WebRTC/WebSockets, криптография, сложные UI-элементы, парсеры, физика) ИИ **обязан**:
     1. Проверить встроенные возможности движка Godot 4.x.
     2. Изучить существующие open-source решения, аддоны и библиотеки на GitHub / Godot Asset Library.
   - Предпочтение отдается зрелым решениям с открытыми лицензиями (MIT, Apache 2.0, BSD) и поддержкой Godot 4+.

2. **Автономная загрузка и интеграция**:
   - ИИ уполномочен и обязан самостоятельно находить, скачивать и распаковывать сторонние аддоны в директорию `addons/` (через `git submodule`, `curl` или GitHub API), регистрируя их при необходимости в `project.godot`.

3. **Паттерн «Glue Code & Facade»**:
   - Роль ИИ — не переписывать готовые библиотеки вручную, а создавать чистые интерфейсы, фасады и адаптеры, бесшовно связывающие внешнюю библиотеку с `EventBus` и архитектурой UniCORE.

## 2. Стандарты качества кода (GDScript 2.0)

1. **Строгая статическая типизация (Strict Typing)**:
   - Любые переменные, параметры функций и возвращаемые значения обязаны иметь явный тип (`var count: int = 0`, `func process_event(data: Dictionary) -> bool:`).
   - Избегать неявного `Variant`, за исключением случаев реальной полиморфной необходимости. Строгая типизация превращает логические галлюцинации в синтаксические ошибки компилятора, которые ловятся мгновенно.

2. **Архитектурный закон: «Call Down, Signal Up»**:
   - Вызовы методов происходят сверху вниз по дереву нод (`parent -> child`).
   - Оповещение о событиях происходит снизу вверх строго через сигналы (`child -> parent`) либо через глобальную шину `core/event_bus.gd`. Никаких прямых связей модулей между собой минуя ядро.

3. **Запрет на плейсхолдеры и срезки (No Placeholders)**:
   - Запрещено оставлять заглушки `# TODO: implement later`, пустые `pass` вместо логики или сокращать код конструкциями `// rest of the code remains the same`. Каждый блок кода отдается в полностью рабочем виде.

## 3. Автономность и инженерная дисциплина ИИ

1. **Self-Verification (Обязательная самопроверка)**:
   - Написанный код не считается готовым, пока не проверен. ИИ обязан выполнить `check-only` и прогнать связанный сьют или общий `res://tests/test_runner.gd`.
   - Если в ходе тестов выявлены ошибки — ИИ устраняет их самостоятельно до финального отчета пользователю.

2. **Атомарность правок (Preserve Context)**:
   - При модификации файлов изменять только целевые участки, сохраняя нетронутыми существующие комментарии, сигнатуры и структуру кода.

3. **Проактивная диагностика (Root Cause First)**:
   - При сбоях или багах не делать случайных правок наугад. Сначала выяснить первопричину (изучить логи терминала, прочитать связанный код, проверить стек вызова), сформулировать гипотезу и только потом вносить исправление.

## 4. Агентный цикл разработки: Plan — Act — Verify & TDAID

1. **Plan (Спецификация и границы)**:
   - Перед кодированием исследовать проект, определить границы изменений (Blast Radius), входные/выходные типы и сигнатуры. Запрещено модифицировать файлы до фиксации плана.
2. **Red (Машиночитаемый контракт)**:
   - Для новой функциональности сначала создается модульный тест в `res://tests/test_<feature>_suite.gd`.
   - Запустить тест и зафиксировать ожидаемый сбой.
3. **Green (Минимальная реализация)**:
   - Написать минимальный чистый код, удовлетворяющий контракту теста.
   - **ЖЕЛЕЗНОЕ ПРАВИЛО**: Запрещено модифицировать или ослаблять проверки (assertions) теста ради его прохождения. Исправляется реализация, а не спецификация!
4. **Verify (Инструментальная валидация)**:
   - Проверить синтаксис: `& "C:\Godot\godot.exe" --headless --path c:\dev\UniCORE --check-only`.
   - Прогнать мастер-раннер: `& "C:\Godot\Godot_v4.0-stable_win64_console.exe" --headless --path c:\dev\UniCORE -s res://tests/test_runner.gd`.

## 5. Предотвращение зацикливания и деградации контекста (Circuit Breaker & Safe Reset)

1. **Строгий запрет на деструктивный Git (`git checkout`, `git reset`, `git restore`)**:
   - Коммиты в проекте выполняются редко (строго при завершении фаз). Любой слепой вызов `git checkout` или `git restore` уничтожит весь накопленный незакоммиченный прогресс текущей фазы. Применение этих команд ИИ категорически **ЗАПРЕЩЕНО**.

2. **Лимит попыток (Circuit Breaker = 3)**:
   - Если ошибка компиляции или упавший тест не исправляются за 3 последовательные попытки, дальнейшие исправления прекращаются во избежание «наслоения костылей».

3. **Безопасный локальный откат и эскалация**:
   - Откатывать изменения разрешено **только точечно и только в границах текущей редактируемой функции/файла** (к состоянию на начало задачи).
   - При срабатывании Circuit Breaker ИИ обязан:
     1. Прекратить модификацию файлов.
     2. Сохранить стабильное рабочее состояние остального проекта.
     3. Вывести пользователю прозрачный отчет: логи ошибок, гипотезы, которые не сработали, и альтернативные варианты решения для согласования.

4. **Контекстная гигиена (Clean Slate)**:
   - Не перегружать сессию огромными простынями логов. При завершении крупного блока работ фиксировать статус в `ROADMAP.md`. Следующая задача начинается с дистиллированного контекста.

## 6. Стандарты тестовых сьютов Godot 4 (`res://tests/`)

1. **Каркас сьюта (`SceneTree`)**:
   - Все тестовые сьюты наследуются от `SceneTree` и завершаются явным кодом возврата: `quit(1 if failed_count > 0 else 0)`.
2. **Запрет на оператор `assert()` в ранерах**:
   - Встроенный оператор `assert()` в debug-сборках Godot аварийно прерывает скрипт до вызова `quit()`, из-за чего процесс в `--headless` **зависает намертво**.
   - Вместо этого использовать функции-хелперы `assert_true(cond, name, msg)` и `assert_false`, аккумулирующие счетчики `passed_count` и `failed_count`.
3. **Асинхронность и безопасность таймеров**:
   - Для тестов, взаимодействующих с деревом нод или сигналами, выполнять `await process_frame` перед обращением.
   - Любой `await` должен быть защищен таймаутом-бэкстопом во избежание вечного ожидания.

## 8. Автоматический регламент: «Закрытие Фазы»

Когда пользователь дает команду на завершение/закрытие фазы (например: *"Закрываем Фазу X"*, *"Фаза X готова, пушь"*):

1. **Верификация тестов**:
   - Убедиться, что новые тесты написаны и общий `test_runner.gd` возвращает 100% прохождение без ошибок.

2. **Актуализация `ROADMAP.md`**:
   - Отметить все чек-боксы закрываемой Фазы `[x]`.
   - Обновить блок `## Текущий статус` вверху `ROADMAP.md` (добавить закрытую фазу с 100% готовности).
   - Переключить фокус на следующую фазу.

3. **Формирование Git-коммита**:
   - Добавить измененные файлы через `git add .` (строго соблюдая `.gitignore`, не трогая `.godot/`).
   - Сформировать подробный коммит по стандарту **Conventional Commits**:
     ```
     feat(phase-<номер>): complete Phase <номер> — <Название Фазы>

     - <Список ключевых фич>
     - <Список созданных/измененных модулей и сцен>
     - Status: All tests passed, ROADMAP updated
     ```

4. **Тегирование (Git Tag)**:
   - Создать аннотированный тег релиза, соответствующий версии фазы (например, `git tag -a v0.3.0 -m "Release Phase 3"`).

5. **Отправка на GitHub**:
   - Выполнить `git push origin <текущая_ветка>` и `git push --tags`.
   - Вывести в чат подтверждение с хешем коммита и ссылкой на GitHub.

---

## 9. Регламент параллельной работы (Разделение сфер: Core vs UI/Design)

1. **Изоляция директорий**:
   - `res://ui/` (включая `ui/theme/`, `ui/shaders/`, `ui/welcome_screen/`, `ui/agent_orb/`, визуальные стили) находится под юрисдикцией **Чата Дизайна**. Системный/Core-чат не вносит туда правки без согласования.
   - `res://core/` и `res://agent/` (сетевой транспорт, LLM, ядро, бэкенд биндов клавиш) находится под юрисдикцией **Системного / Core-чата**.

2. **Интеграционный протокол**:
   - Связь UI и Core осуществляется исключительно через публичные фасады: `EventBus` (сигналы), `SettingsManager` (настройки) и `SpaceViewport` (монтирование слоев). Никаких прямых зависимостей от внутренних переменных.
