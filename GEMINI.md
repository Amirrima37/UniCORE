# UniCORE — Базовые правила и контекст проекта

## 1. Профиль проекта
- **Движок**: Godot 4.0.stable (official 92bee43ad)
- **Исполняемый файл**: `C:\Godot\godot.exe` (консольный: `C:\Godot\Godot_v4.0-stable_win64_console.exe`)
- **Архитектура**: Модульное ядро, Detroit Liquid Glass UI, P2P & Agent
- **Документация**: `ARCHITECTURE.md`, `ROADMAP.md`

### Специфика Godot 4.0-stable:
1. Запрещен вызов `ClassName.has_method(...)` напрямую на имени класса.
2. Примитивы в лямбдах захватываются по значению. Для изменения оборачивать в массив: `var done = [false]`.
3. `Callable.bind(...)` добавляет связанные аргументы *в конец* сигнатуры.

## 2. Разделение ролей и зон ответственности чатов

В проекте параллельно работают специализированные чаты. Каждый чат занимается **только своей сферой**:

1. **Промпт-чат / Оркестратор**:
   - **Сфера**: Декомпозиция задач, проектирование контрактов, подготовка структурированных ТЗ и промптов для других чатов.
   - **Правило**: **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** писать модульные тесты, запускать Godot и выполнять тестовые раннеры. Продукт этого чата — четкие инструкции, архитектурные схемы и спецификации.

2. **Чат Дизайна и интерфейсов (UI/Design)**:
   - **Сфера**: `res://ui/` (темы, шейдеры, панели Detroit Liquid Glass, верстка).
   - **Правило**: Работает с визуалом. Не лезет в `res://core/` и сетевой транспорт.

3. **Системный чат (Core / Dev)**:
   - **Сфера**: `res://core/`, `res://agent/`, модульная система `res://modules/`, сетевые протоколы.
   - **Правило**: Пишет чистый GDScript 2.0 с типизацией. Не запускает лишних тестов.

## 3. Регламент работы с тестами и терминалом (Экономия токенов и времени)

> [!IMPORTANT]
> **ТЕСТЫ — ЭТО НЕ САМОЦЕЛЬ.** Запрещено парализовать работу постоянным запуском тестовых сьютов!

1. **Когда тесты ЗАПРЕЩЕНЫ**:
   - Ответы на вопросы, обсуждения, консультации, проектирование архитектуры.
   - Написание промптов, документации, markdown-файлов.
   - Правка визуальных шейдеров, тем или верстки UI.
   - Любые не связанные с изменением сложной логики задачи.

2. **Когда запускаются тесты**:
   - **Мастер-раннер (`test_runner.gd`)** запускается **СТРОГО в двух случаях**:
     1. Пользователь прямо написал команду: «Запусти тесты» / «Проверь мастер-раннер».
     2. На этапе «Закрытия Фазы» перед формированием финального отчета.
   - **Во время обычной разработки**: запускать полный сьют всех тестов **ЗАПРЕЩЕНО**. При необходимости разработчик проверяет **только один конкретный файл**, над которым работает, либо выполняет быстрый `--check-only`:
     `& "C:\Godot\godot.exe" --headless --path c:\dev\UniCORE --check-only`

3. **Безопасность тестов Godot 4**:
   - Все тестовые скрипты хранятся строго в `res://tests/`.
   - В тестах **запрещен встроенный `assert()`** (он вешает процесс в `--headless`). Используются счетчики и `quit(code)`.

## 4. Качество кода и принципы разработки (GDScript 2.0)

1. **«Reuse First» (Готовые решения)**:
   - Не писать велосипеды. Для P2P, криптографии, специфических парсеров использовать встроенные классы Godot или готовые open-source аддоны из интернета/GitHub.
   - ИИ может скачивать и распаковывать готовые аддоны в `addons/`.

2. **Строгая статическая типизация**:
   - Все переменные, аргументы и функции должны иметь явные типы (`var count: int = 0`, `func foo() -> void:`).

3. **Запрет на плейсхолдеры**:
   - Никаких `# TODO: implement later` или пустых заглушек в готовом коде.

4. **Запрет на деструктивный Git**:
   - **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНЫ** команды `git checkout`, `git reset`, `git restore`. Коммиты делаются редко, сброс сотрет прогресс пользователя. Откат при ошибках делать только точечно внутри редактируемого файла.

5. **Ограничение попыток (Circuit Breaker = 3)**:
   - Если код не компилируется или задача не решается за 3 попытки — остановиться, вернуть исходный файл и описать проблему пользователю, а не ходить кругами.

## 6. Регламент: «Закрытие Фазы»

Выполняется **только по прямой команде пользователя** (например: *«Закрываем Фазу 3»*):
1. Запустить общий `& "C:\Godot\Godot_v4.0-stable_win64_console.exe" --headless --path c:\dev\UniCORE -s res://tests/test_runner.gd`.
2. Обновить чекбоксы и статус в `ROADMAP.md`.
3. Сформировать коммит по Conventional Commits и тег (`git tag -a v0.X.0 -m "..."`).
4. Выполнить `git push origin <ветка>` и `git push --tags`.
